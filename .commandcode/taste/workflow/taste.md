# workflow
- Prefers thorough analysis and planning before writing code: expects project exploration, gap analysis, and a structured plan (phases, ordered steps) before any implementation begins. Confidence: 0.95
- When the user explicitly asks to enter plan mode ("pases a plan mode"), expects the agent to actually switch into it, explore the relevant code first (parallel sub-agents), then surface design decisions as multiple-choice questions before writing the plan. Confidence: 0.75
- When deciding whether to escalate to planning mode (or a similar process step), user defers to the agent's judgment — explicitly authorizes switching into planning mode if the agent deems it necessary ("si considerás necesario pasar al planning mode, hacélo") rather than waiting to be asked. Confidence: 0.60
- Wants implementation work to be documented: expects a clear summary of what was built, which files were created/modified, and what each piece does — not just the code itself. Confidence: 0.80
- Gathers reference material from competitor/peer products (HTML, screenshots, feature lists) to ground planning in concrete examples rather than abstract feature descriptions. Confidence: 0.75
- Provides detailed, implementation-ready design specs when requesting features — exact hex colors, layout structure, and micro-interactions — and expects the agent to honor them faithfully rather than interpreting loosely. Confidence: 0.70
- Verifies code compiles and builds after every change: runs TypeScript type-check (`tsc --noEmit`) and production build (`next build`) as a matter of course before declaring work done. Confidence: 0.70
- Prefers completing and polishing existing features (e.g., responsive design, UX polish) before starting a new major feature or product; values shipping quality over expanding scope prematurely. Confidence: 0.65
- For planned-but-not-yet-shipped features (e.g., a feature "on the roadmap" but not yet in the public release), prefers to comment out the code and add a documented reversal path in PRODUCT.md (or equivalent) rather than delete it — values the ability to reactivate later with minimal effort, even at the cost of carrying dead code temporarily. Confidence: 0.80
- When offered design/architectural choices via `ask_user_question` with a marked "Recommended" option, tends to pick that recommended option; trusts the agent's framing of defaults rather than agonizing over the alternatives. Confidence: 0.70
- Prefers security/captcha widgets to be invisible or minimal — dislikes large visible challenge rectangles that clutter forms; values clean, minimal form design. Confidence: 0.60
- Before mutating global/system state (e.g., reinstalling a globally-installed package or rewriting a system binary), expects the agent to diagnose first and then ask for confirmation rather than running the change unprompted. Confidence: 0.60
- Reviews work incrementally and gives feedback one issue at a time rather than in a single large batch; signals upcoming rounds explicitly ("te voy a ir diciendo los detalles que me voy encontrando"). Confidence: 0.70
- When requesting a change, scopes it explicitly: if a feature is hard or risky, user prefers to discuss it and defer ("si es algo muy difícil charlemoslo y lo podemos dejar para después"); if it's simple, wants it done in the same round. Expects the agent to gauge complexity and either ship or surface a discussion, not silently skip the request. Confidence: 0.70
- When a fix attempt makes things worse (introduces regressions, breaks previously-working surfaces, produces "quedó muy mal"), prefers a **surgical revert to the last known-good state** over trying to patch the new broken code; will explicitly say "revertí los cambios" and proactively suggest git as the recovery tool. Expects the agent to preserve unrelated working work (other files, other features touched in the same session) and only restore what broke. Confidence: 0.90
- Values industry-standard, professional architectural patterns over "it works" workarounds; wants to know how established platforms do it and aligns with those approaches (e.g., presigned URLs over sequential file uploads through the server). Confidence: 0.70
- Disable action buttons (publish, update, unpublish) during async operations like uploads to prevent double-submission and signal that work is in progress. Confidence: 0.75
- For direct database operations (schema changes and data mutations like plan/submission-limit updates), prefers raw SQL statements to paste into the Supabase SQL Editor over CLI migration commands (`supabase db push`); explicitly asks for copy-pasteable SQL and chooses to stay manual even when installing the CLI is offered as the "recommended" option. Confidence: 0.92
- Expects the "ponytail" skill to be active when coding — considers it important and asks the agent to activate it if it's not already on. Three levels available: lite, full, ultra. Confidence: 0.85
- At the start of a working session, explicitly asks the agent to first read and understand the whole project (purpose, stack, structure, key files) to build context before any task begins. Confidence: 0.60
# testing
- When testing or demoing a product surface (e.g., the showcase directory), prefers seeding realistic, varied data — multiple users across subscription tiers and many entries with varied categories/attributes — rather than a minimal or empty dataset. Confidence: 0.55
- Seeds backdated entries (e.g., a month old) specifically to test time-window filtering like "this week's launches", verifying that stale items are correctly excluded. Confidence: 0.55

# documentation
- Values cross-session continuity: proactively considers whether documentation is needed so a new session can quickly understand the project structure and purpose, and is open to maintaining/updating project docs (README, PRODUCT.md) to support fast onboarding. Confidence: 0.55
- For operational/infrastructure tasks (e.g., preparing for a production launch), prefers a written step-by-step guide with a prioritized checklist (what blocks launch vs. what can wait) saved as a dedicated doc file, rather than only a chat explanation. Confidence: 0.60
- Maintains a dedicated project-context document (`.commandcode/contexto-proyecto.md`) and proactively asks for it to be rewritten to reflect the actual current state of the project (product name, stack, accounts/infra, routes, DB schema, features, limitations, key files) as the project evolves — not left accumulating stale placeholders or outdated names. Confidence: 0.75
- Tracks known bugs and technical debt in a phased plan document (REDESIGN_PLAN.md) with numbered sections (e.g., 3.3) and works through those items across sessions ("revisemos el tema de la paginación buggeada"); expects such docs corrected/updated when they describe already-resolved states instead of staying stale. Confidence: 0.60
# code-quality
- Prefers a single source of truth for logic/rendering that would otherwise be duplicated across surfaces (e.g., the same template layout rendered in both the public page and the editor preview); flags duplicated code and wants it unified into one shared component rather than kept in sync manually. Confidence: 0.75
- Applies the "ponytail" principle actively: prefers native HTML+CSS over libraries, deletes code over adding it, marks known ceilings with `ponytail:` comments, and pushes back on scope creep (e.g., building a data-driven icon registry when 9 hand-rolled functions suffice). Confidence: 0.80
- Verifies build compiles not just at the end of a multi-phase task, but between phases when adding new files/components — catches type errors early before they compound. Confidence: 0.70
- For data migrations of stored values (e.g., legacy emoji icons in DB rows, old default colors), prefers the cheapest non-breaking path: change the *default* for new items and accept legacy values rendering as-is, rather than writing a one-time migration script. Treats DB content as append-only history. Confidence: 0.75
- Prefers tolerating short duplication (e.g., the same 3-line legacy-color migration inlined in two pages) over extracting a shared helper across the server/client boundary. Explicitly rejects "scope creep de abstracción" for small, local migrations. Confidence: 0.75
- Will not convert a server component into a client component just to share a 3-line active-link pattern. Server-side data fetching (e.g., `getUser`) is more valuable than DRYing a tiny UI helper; lets the duplication stand and moves on. Confidence: 0.80
- The `ponytail` skill is used to annotate code with explicit `// ponytail:` comments when making a deliberate non-ideal choice (e.g., leaving a `<label>` wrapper inside a `<td>`, inlining duplicate migration logic, leaving an unused field in the DB). These comments serve as durable "why is this like this" breadcrumbs for future readers. Confidence: 0.80
# tooling
- File tools choke on Next.js dynamic-route paths containing brackets (`[id]`): `read_file` silently returns empty content even though the file exists, and `edit_file` rejects relative paths. Reliable workaround: read these files via shell (`cat -n`) and invoke `edit_file` with the full absolute path (e.g., `/Users/lvenezia/Desktop/baul/list/src/app/api/projects/[id]/export/route.ts`). Confidence: 0.75
- VS Code may not render installed skills (impeccable, ponytail) in its UI even when they exist on disk; the skills are still active for the agent via `activate_skill` — don't waste time debugging the editor when the agent tool works. Confidence: 0.65
# design-system-workflow
- For large design-system refinement tasks, uses plan mode with parallel `explore` sub-agents to map the codebase (icon usage, form controls, templates, placeholders, tabs) before writing any plan. Each sub-agent gets a focused, scoped question with specific deliverables and depth. Confidence: 0.80
- After exploration, surfaces only the genuinely open decisions as `ask_user_question` multiple-choice questions (typically 1-2 questions), marks a "Recommended" option, and trusts the recommended pick — doesn't ask about things with obvious answers. Confidence: 0.75
- Plan documents are written to disk (e.g., `~/.commandcode/plans/*.md`), not just shown in chat; structured with: context, architecture, per-file changes, execution order (numbered phases), verification steps, files to touch/create, and explicit "do not touch" sections. Confidence: 0.80
- Design system changes must update documentation (DESIGN.md, CHANGELOG.md, PRODUCT.md) as part of the same change, not as a follow-up — the docs are part of the deliverable. Confidence: 0.75
- When user feedback has multiple valid interpretations, the agent should pick the deeper/more ambitious interpretation rather than the surface-level fix — e.g., interpreting "the open button should be clearer" as "build a real preview route" rather than "relabel the button". When it gets the interpretation wrong, it should own the miss openly and propose the better path before being asked twice. Confidence: 0.80
